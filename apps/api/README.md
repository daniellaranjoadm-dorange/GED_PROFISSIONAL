# Core read-only API v1

Four GET endpoints are available at `/api/v1/projects/`,
`/api/v1/projects/<int:id>/`, `/api/v1/documents/`, and
`/api/v1/documents/<int:id>/`.

Existing Django sessions and the existing `ged.visualizar` RBAC permission
are required. Anonymous GETs return JSON 401; denied users receive JSON 403.
Master/superuser behavior comes from the existing permission function.
No login redirects, new authentication mechanism, CORS or packages are added.

## Identity and visibility

Documents are revision-level resources: `id` is `Documento.pk` and `revision`
is that row's persisted revision. Only active, non-deleted documents are visible.
`master_id` is the persisted master FK. Current-revision fields use the stored
master pointer, never a recalculation. A missing, inactive, deleted or
inconsistently linked current revision yields null current fields and false
`is_current_revision`; no pointer is repaired. Cross-project pointers are not
reinterpreted. Project assignment is taken only from the returned revision.

Project list/detail include all persisted projects, including inactive projects,
with the stored `active` flag. They expose only `id`, `name`, `client`, `active`.

Document keys: `id`, `master_id`, `document_number`, `title`, `revision`,
`current_revision_id`, `current_revision`, `is_current_revision`, `project`,
`discipline`, `document_type`, `status`. Project is `{id, name}` or null.
Nullable metadata preserves stored null/blank values. No enrichment, paths,
financial data, deletion metadata, files or workflow data are exposed.

## Filtering and pagination

Document lists accept `project_id=<positive integer>` matching the exact FK.
An existing project with no eligible documents returns an empty list. Invalid
or nonexistent project IDs return 400. Without a filter, unassigned documents
are included. `project=HANDY`, GLP and MR1 aliases are unsupported and return
400, as do unknown or repeated query parameters. Detail endpoints accept no
query parameters.

Both lists accept `page` (default 1) and `page_size` (default 50, maximum 200).
Values must be positive integers; oversize page sizes and out-of-range pages
return 400. Results are ordered by ascending PK. An empty list has page 1 and
total_pages 1. The envelope is `{count, page, page_size, total_pages, results}`.
Offset pagination is deterministic for unchanged data, not a snapshot across
concurrent operational updates.

## Errors and methods

Errors generated by these views use
`{"error": {"code": "not_found", "message": "Document not found."}}`.
Codes: `authentication_required` (401), `permission_denied` (403),
`invalid_query` (400), `not_found` (404), `method_not_allowed` (405).
Valid integer detail IDs outside the visible queryset return 404.
Unknown URL patterns and framework/server errors remain Django-managed.

Only GET is supported. POST/PUT/PATCH/DELETE/HEAD/OPTIONS reaching the API
wrapper return 405 with `Allow: GET`; HEAD has no response body. Method checking
precedes authentication. Existing CSRF middleware may reject unsafe requests
first with Django's 403 response. CSRF is not bypassed or weakened.
API responses use `Cache-Control: private, no-store`.

## Safety and tests

Selectors only read core document/project/master tables; serializers are explicit
functions. No synchronization, lifecycle, reconciliation, registration, automation
or mutation services are called. There are no models or migrations in this app.

Run `python manage.py check` and `python manage.py test apps.api.tests`.
Django's test runner creates an isolated test database. Test fixtures mutate only
that database. Never point a test database at the operational SQLite file.
Tests cover RBAC, schemas, pagination, visibility, revision pointers, method/CSRF
rejection and captured SQL proving API requests contain no writes or automation
table reads.
